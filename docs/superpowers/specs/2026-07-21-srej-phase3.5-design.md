# tncd 2.0 Phase 3.5 (Full SREJ / Selective Repeat) Design

**Status:** Approved design.
**Umbrella:** `2026-07-14-tncd-2.0-go-port-design.md`.
**Predecessor:** `2026-07-20-ax25-v22-phase3-design.md` (phase 3 deferred full SREJ to here).
**Date:** 2026-07-21.

## Purpose

Add the *receiver* half of AX.25 2.2 selective reject (SREJ): when tncd detects
a gap in the incoming I-frame stream, buffer the out-of-order frames and request
retransmission of just the missing frame, instead of the current REJ /
go-back-N. This is the selective-repeat throughput win for the Winlink
**download** direction (CMS→client, where tncd is the receiver) over a lossy
path — one lost frame costs one retransmission instead of a whole window.

## Framing: what phase 3 already built vs. what this adds

Phase 3 built the **sender** half: tncd already handles *receiving* an SREJ from
a peer and retransmitting the single requested frame (`dispatchS`, SREJ branch),
and it has the `SREJ` frame type, the mod-128 codec, and the XID codec.

Phase 3.5 builds the **receiver** half: gap detection, a receive-reassembly
buffer, SREJ *generation*, and in-order delivery on gap-fill. It also flips the
XID advertisement from `SREJNone` to `SREJSingle` so the capability is actually
negotiated on. Together these close the loop: an SREJ-enabled link uses
selective repeat in both directions.

## Scope

- **Single-SREJ only** (ratified AX.25 2.2 + Direwolf's default). One SREJ per
  missing N(S). SREJ is response-only (per X.25 §2.4.6.4, which Direwolf follows
  because the AX.25 2.2 spec is thin on SREJ).
- Receive-reassembly buffer with strict in-order delivery.
- Per-port `srej = on | off` config, default **on** (effective only on
  mod-128 links with an SREJ-capable peer).

Non-goals (deferred / not planned):

- **Multi-SREJ** (info field listing several missing frames) and XID
  `srej_multi` up-negotiation. This is a post-2.2 in-progress-revision
  extension; Direwolf implements only a partial form and skips the range
  encoding. Not worth it for tncd↔Direwolf.
- The SREJ **range-encoding** form (Direwolf skips it too).
- **Own-receiver-busy / RNR** interactions in the SREJ path — tncd has no
  receiver-busy state; follow the simpler path.

## Reference

Direwolf 1.8.1 `ax25_link.c` remains the reference. Load-bearing facts:

- SREJ is **mod-128 only** in Direwolf (`:2814` errors on "SREJ in basic
  modulo 8 mode"), so phase 3.5 is inherently gated behind `ax25_version = 2.2`.
- The receive path is X.25 §2.4.6.4-based (`:2821-2822`), using an
  `rxdata_by_ns[128]` buffer (`:443`), storing in-window out-of-order frames
  (`:2825-2835`) and delivering contiguously from V(R) (`:2713-2729`).
- SREJ is **response-only** (`:2203-2204`).
- Duplicate-SREJ suppression: Direwolf 1.5 "don't generate duplicate requests
  for gaps in the same transmission" (`:2875-2877`).
- `srej_enable` means "is the other end capable of processing SREJ — am I
  allowed to send it" (`:273`); it starts `srej_single` for v2.2 and is tuned
  by XID.

## 1. Enablement & negotiation

New per-conn `srejEnabled bool`, true iff **all** of:

1. the port's `srej` config is on, **and**
2. the link is mod-128 (`c.modulo == 128`), **and**
3. the negotiated SREJ mode is `>= SREJSingle` — learned from an XID **exchange**
   (see below). Until an XID exchange completes, `srejEnabled` is false and the
   link uses REJ (a safe default; it flips on when the exchange resolves).

SREJ is only meaningfully enabled once each side knows the other can process it,
which requires an XID exchange. XID is sent by the **connection initiator**
(Direwolf's model). tncd plays both roles:

**tncd as answerer (peer initiated — e.g. an inbound connect to tncd).** The peer
sends an XID **command**; `dispatchXID` already handles it. Change: when the
port's `srej` config is on, advertise `SREJSingle` (not `SREJNone`) in the XID
response, and set `srejEnabled` from the negotiated value (`min` of our advertised
mode and the peer's — i.e. `SREJSingle` iff the peer's command advertised
`>= SREJSingle`, else `SREJNone`).

**tncd as initiator (tncd connected out — the Winlink download case).** Because
the answering peer does not send XID, tncd must **initiate** the XID exchange
itself (this is what Direwolf's initiator does; it is a deliberate, scoped
reopening of phase 3's "never initiate XID"). When an outgoing v2.2 connect is
confirmed (SABME → UA, i.e. in `dispatchUA` on the `Connecting → Connected`
transition) *and* `srej` config is on *and* `modulo == 128`, tncd sends an XID
**command** (P=1) advertising `SREJSingle`, window (= our `MaxWindow`), N1 = 256,
modulo 128. `dispatchXID` is extended to handle the peer's XID **response**
(previously ignored): parse it and set `srejEnabled` from the negotiated value,
sending no reply. A single XID command is sent (no dedicated retry timer); if the
command or response is lost OTA, `srejEnabled` stays false and the session simply
uses REJ — data still flows correctly, just without selective repeat. (A retry is
a possible phase-4 refinement; Direwolf's MDL retry machinery is out of scope.)

Advertising `SREJSingle` is safe with a REJ-only peer: XID negotiation keeps the
lower value, so the link falls back to REJ and `srejEnabled` stays false. With
`srej = off`, tncd advertises `SREJNone` and does not initiate XID — exactly
phase-3 behavior.

The `srejEnabled` decision is identical in both roles (`configOn && modulo==128 &&
negotiatedSREJ >= SREJSingle`); factor it into one helper (`setSREJFromXID`) called
from both the command and response branches of `dispatchXID`.

Because phase 3 already handles *receiving* SREJ, once `srejEnabled` is true the
peer (Direwolf) may send tncd SREJ and `dispatchS` handles it unchanged.

## 2. Receiver reassembly (`dispatchI`)

New per-conn `rxBuf map[uint8]rxEntry` (keyed by N(S), value `{pid uint8; info
[]byte}`), mirroring Direwolf's `rxdata_by_ns[]`. On an inbound I-frame when
`srejEnabled`:

- **In sequence (`N(S) == V(R)`):** deliver it to the client, then **walk
  `rxBuf` forward** — while `rxBuf[V(R)+1]` exists, deliver it, advance V(R),
  delete it from `rxBuf` — until a hole. Then send the ack (§3). This is the
  gap-fill path that flushes buffered frames in order.
- **Ahead, in window (`0 < (N(S) − V(R)) mod modulo ≤ window`):** store
  `{pid, info}` in `rxBuf[N(S)]` (idempotent: overwrite on duplicate). Do **not**
  advance V(R); do **not** deliver. Generate an SREJ for the gap (§3).
- **Duplicate (`N(S) == V(R)−1` etc.) or outside window:** discard (existing
  behavior; honor P=1 with an RR/SREJ-F1 response as today).

When `srejEnabled` is false, `dispatchI` takes the **existing phase-3 REJ /
go-back-N path unchanged** (this is the regression guard).

**Safety invariant:** frames reach the AGWPE client **only in strict sequence**
— `rxBuf` holds out-of-order frames until the gap fills, so the client never
sees out-of-order data even mid-recovery. A reassembly bug therefore fails safe
(the link stalls and T1 recovers) rather than corrupting the delivered stream.

## 3. SREJ generation

When a gap is detected (a frame is stored ahead of V(R)), send an **SREJ
response** for the earliest missing frame that has **not already been
requested**:

- `N(R)` = the lowest sequence number in `[V(R), N(S))` that is neither present
  in `rxBuf` nor already in the dedup set `srejSent` (§below). In the common
  single-gap case this is V(R) itself; when V(R)'s hole is already outstanding
  and a *later* frame also arrives ahead, `N(R)` is that later hole.
- Set **F=1** iff `N(R) == V(R)` (asking for the earliest expected frame informs
  the peer of our V(R) and doubles as an acknowledgement, so no separate RR is
  needed); **F=0** otherwise. This mirrors Direwolf's `f = allow_f1 && (nr ==
  V(R))` (`:3218`).
- SREJ is a **response** frame (`respFrame(..., ax25.SREJ, ...)`).
- **Duplicate-SREJ suppression:** a per-conn `srejSent map[uint8]bool` records
  which N(S) we have already requested. Add `N(R)` to it when we send the SREJ;
  skip generating an SREJ for any N(S) already in the set. Clear an entry when
  that frame arrives (stored in `rxBuf` or delivered) or when V(R) advances past
  it. This prevents the "ask twice, peer sends twice" waste Direwolf documents.
- No new timer: the *sender's* T1 backstops a lost SREJ (it will poll and
  retransmit), so SREJ generation is fire-and-forget.

## 4. Config & CLI

`internal/config`: add `srej = on | off` to `[client.N]` (default **on**);
add `"srej"` to `knownClientKeys`; parse to `Port.SREJ bool`; thread into
`PortParams.SREJ` via the bridge (same pattern as `AX25Version`). Update
`example.ini` with a commented note that it is effective only on v2.2/mod-128
links and auto-falls-back to REJ with non-SREJ peers. New `Conn` fields
(`srejEnabled`, `rxBuf`, `srejSent`) are cleared in `newConn`/`resetSeqs`.

## 5. Testing

**Unit — the deterministic proof of SREJ behavior (no loss needed):**

- Reassembly: on an `srejEnabled` conn, feed `dispatchI` N(S) = 0, 2, 3, 1 and
  assert: frame 0 delivered immediately; 2 and 3 buffered, not delivered; an
  SREJ for N(R)=1 emitted exactly once; on frame 1, frames 1,2,3 delivered in
  order and V(R) advances to 4.
- Dedup: repeated in-window gaps do not emit a duplicate SREJ for the same N(S).
- F-bit: an SREJ requesting V(R) carries F=1.
- XID (answerer): with `srej` on, the XID response advertises `SREJSingle`; a
  peer XID command advertising `SREJNone` yields `srejEnabled=false` and the REJ
  path; a command advertising `SREJSingle` yields `srejEnabled=true`.
- XID (initiator): an outgoing v2.2 connect with `srej` on sends an XID
  **command** (P=1, advertising `SREJSingle`) after UA; a peer XID **response**
  advertising `SREJSingle` sets `srejEnabled=true` (advertising `SREJNone` leaves
  it false). With `srej=off`, no XID command is sent on connect.
- Gating regression: `srej=off`, or mod-8, or a REJ-only peer → `srejEnabled=
  false` → `dispatchI` takes the existing REJ / go-back-N path **byte-for-byte
  unchanged**.
- Safety: across all the above, the client never receives out-of-order data.

**E2E:** extend the Direwolf-v2.2 test to assert the link negotiates SREJ
enabled (Direwolf log shows SREJ, not REJ-only) and a clean round-trip still
succeeds. A clean PipeWire cross-link has no loss, so this proves **negotiation
+ no-regression only, not recovery**.

**OTA gate (differs from phase 3):** phase 3's OTA needed only a clean mod-128
round-trip; phase 3.5's must run over a **genuinely lossy path** (marginal
signal or deliberate attenuation) so SREJ actually fires. Pass criteria: SREJ
frames observed on-air; correct selective recovery; clean delivered data despite
loss; and throughput visibly better than the same path with `srej=off`
(go-back-N). New `docs/superpowers/specs/phase3.5-ota-checklist.md`.

## 6. Sequencing

Branch `feature/srej` from `main` (phase 3 merged at `8edffc3`); merge
`--no-ff` after unit + e2e + OTA pass. No version bump or tag — SREJ rides to
the eventual v2.0.0 tag (phase 4). This is the last connected-mode feature
before phase 4 (platforms & release).

## Exit criteria

1. All new + existing `go test` pass; the phase-3 REJ / go-back-N path is
   byte-for-byte unchanged when `srejEnabled` is false.
2. E2E: Direwolf-v2.2 link negotiates SREJ enabled; clean round-trip succeeds.
3. OTA: over a lossy real path, SREJ frames observed, selective recovery
   correct, data clean, throughput better than `srej=off` — logged in the
   phase-3.5 OTA checklist.
